# ADR-0003 — 全项目横屏优先与 1280×720 设计基准

> 日期：2026-10-26 | 版本：v1.0 | 状态：`accepted`（用户本轮及 Issue #1 评论明确确认） | 关联 Feature：FEAT-001、002、005–008、010–012

## 背景及约束

整个《一二布布游戏屋》需要统一大厅、选角、各游戏及未来好友房的使用方向，平等展示一二（小白熊）和布布（小棕熊）。用户已在 [Issue #1 横屏优先基线](https://github.com/muddyrain/yier-bubu-gamehouse/issues/1#issuecomment-6418493257) 确认首发采用横屏。旧 720×1280 Startup 预览是真实历史证据，不能证明修改后横屏可运行。

本次仅修改现有 P1-01 工程基线；保留真实引擎生成的场景结构、Meta UUID 和 SmokeTest 生命周期。AGENTS 与 DEV_ENVIRONMENT 的 OS 安全规则不变；本轮 Windows 也不启动 GUI，横屏复验需要本次具体许可。

## 决策

- 首发全项目统一 **Landscape 横屏**，设计基准 **1280×720（16:9）**，适用于大厅、选角、塔防、黄金矿工、合成、贪吃蛇、公共界面及未来好友双人房；暂不引入单游戏动态旋转。
- 1280×720 是制作坐标基准，不锁定设备物理分辨率。安全区、文字可读性和触控范围由后续真实设备验收。
- P1-01 将 Project Settings 默认 Canvas 与既有 Startup Canvas 分别改为横屏；Canvas 中心为 (640, 360)，UITransform 为 1280×720，现有正交相机半高为 360，保持 Canvas/Widget/脚本关联。
- Startup 采用 Fit Width=true、Fit Height=true，等比完整显示设计区域，接受黑边；双角色使用同尺寸几何占位，在中心两侧对称展示。该设置是启动基线，不提前替代正式玩法的布局设计。
- 原本适合窄高场地的合成等玩法，在横屏内保留居中的窄高逻辑容器，左右放置分数、图鉴或操作说明，保持玩法坐标与外围 UI 分离；具体容器大小和控件需在对应 Feature 实现时验证，本轮不开发玩法。
- 后续微信构建选用 Landscape，并核对真实生成的 `game.json`；本轮不构建，不创建占位输出文件。官方依据见 [REFERENCES](../REFERENCES.md)。

## 考虑过的替代方案

| 方案 | 取舍 |
| --- | --- |
| 全项目竖屏 | 不符合已确认的产品方向；横向战场、双人并列和目录需要重新组织 |
| 每款游戏自行旋转 | 会增加大厅切换、输入坐标、安全区和未来双人房的一致性成本；首发不采用 |
| 横屏内拉伸全部内容铺满 | 矩形比例、文字和玩法坐标可能失真；采用等比显示与独立容器布局 |
| 横屏固定宽度并裁剪高度 | 宽屏可能裁掉上下信息；启动检查先使用完整显示策略 |

## 理由、代价与后果

统一方向减少跨游戏导航与角色展示的差异；横向空间可同时容纳双方角色及玩法信息。代价是合成等窄高玩法需要外围 UI 重新编排，4:3 和超宽屏可能留边，缺口屏的可操作区域也不能靠设计分辨率推定。

产品方向已经接受，工程和画面是否正确仍需验证。工程 JSON 的静态修改及 TypeScript 通过，不等于 Cocos 已重新导入或实际渲染通过；旧竖屏报告和截图原样保留。

## 验证和回退条件

1. 安全 CLI 分别检查默认分辨率、既有 Canvas 尺寸/中心/相机、对象和脚本引用；比对本轮前后 Meta、场景对象 ID 和私有配置，保留失败记录。
2. 获得当次许可后，在 Windows 3.8.8 运行横屏 Startup，检查完整标题、双方名称/占位、自动 start、停止/重启和阻断性脚本错误；比较 16:9、4:3、超宽屏至少两类额外比例。未执行为 `not_run`。
3. 微信设备方向、缺口/安全区、触控与性能在后续正式构建和真机阶段验证；不由桌面结果推定。
4. 若发生裁切、重叠或文字不可读，先检查 Canvas/相机/适配及 UI 布局根因。影响首发可用性且无法通过横屏布局解决时，提交证据供用户重新决策；不擅自改回竖屏或加入动态旋转。
5. 若工程无法导入，可经审查恢复本轮修改前的对应文件内容，不重建场景或重生成 UUID；全局方向变更须新决策取代本 ADR，并重新验收。
